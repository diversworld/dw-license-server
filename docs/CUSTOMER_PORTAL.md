# Customer portal

Administrators with global USER_MANAGE access can now use the **Users → Add user** form. It defaults to ROLE_CUSTOMER with globalAccess disabled. Enter name/email, assign the responsible customer(s), and enter the initial password twice (at least 12 characters). Only a password hash is stored; creation rejects missing assignments, weak/mismatched passwords and forged Super Admin roles. Creation remains unavailable to scoped staff and portal users. Existing account edits preserve their passwords. Alternatively create users with ROLE_CUSTOMER, disable globalAccess and explicitly assign their customers. The User form validates that combination; the portal independently refuses misconfigured global customer accounts. This role inherits ROLE_USER, not administrative viewing/operation roles. Existing administrative roles are unchanged. CLI provisioning uses app:admin:create --role=customer --customer=UUID and an interactive hidden password; multiple --customer values explicitly scope the account. Customer logins and the home route direct to /portal; locales de/en/fr/es are supported. Optional/required 2FA enrollment, change and recovery remain available to customer users.

Lists, direct license IDs, installations, forms and action history inherit the customer filter and object-level guards. License pages show expiry and features. Downloads require CSRF and a selected active installation belonging to that license; issuance reuses the existing locked LicenseManager and checks expiry, customer/product status and installation binding. Downloads are attachment responses with no-store/private and nosniff. No license key or token is placed in a URL. Index/detail/form pages also use no-store.

Domain changes require a reason and PORTAL_DOMAIN_CHANGE permission. The persisted window defaults to two changes per license in 30 days, configurable by PORTAL_DOMAIN_CHANGE_LIMIT and PORTAL_DOMAIN_CHANGE_WINDOW_DAYS. A shared database row lock serializes changes. Hostnames are validated server-side; occupied/unchanged domains, expired/disabled licenses and exhausted limits are rejected. The action history stores actor, UTC-compatible stored time, reason, installation ID and before/after domains; ORM changes join the audit chain. Migration Version20261003103656 adds nullable JSON details without rewriting past records.

After a domain change, download and install a fresh signed file. The previous domain binding cannot refresh online, but an already disconnected client holding an old offline token is subject to its signed expiry; changing server data cannot invalidate offline signatures remotely. Installation allocation limits remain unchanged. Portal limits do not grant customers license renewal, pause/revocation or global administration rights. No customer portal has been deployed and no production migration was executed.
