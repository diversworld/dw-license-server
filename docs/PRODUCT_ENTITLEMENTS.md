# Declarative rights and license plans

Products define allowed features, required features, an installation cap and optional positive integer ceilings per feature. Identifiers use ASCII letters/digits and `_.:-` (1–64 characters). Required features must be allowed. A quota can only refer to an allowed feature. When issuing a feature with a declared quota ceiling, its license/plan must supply an explicit positive quota no larger than that ceiling. No quota means the product has not declared a numeric ceiling for that feature. License issuance and deliberate feature/installation/quota/product edits validate these rules server-side, including through the management API and ORM persistence guards. Forms use lists and feature/limit pairs, not raw JSON.

`LicensePlan` defines product, name, duration (1–36500 days), features, quotas, installation count and nullable update entitlement. Administrators manage/deactivate plans; they cannot hard-delete them from the UI. Staff with `LICENSE_CREATE` create a license through **Create license from plan**, selecting only an authorized active customer. The product, plan and customer are rechecked under database locks. The management API additionally accepts a `plan` UUID; omit `expiresAt`, `features`, `quotas` and `maxDomains` overrides when selecting a plan. Customer scope, credential scope and idempotency still apply. For custom issuance supply a future `expiresAt` and valid explicit rights.

```json
{"product":"example-product","plan":"00000000-0000-4000-8000-000000000001","reason":"Annual contract 1042"}
```

Each license stores a versioned snapshot of the applicable product rules and, for plan issuance, the plan identity/name/duration/grants. Later plan/product edits affect **new grants only**. Existing features, installation limits, quotas, expiry and update rights stay unchanged; validation/refresh use the saved rules. A deliberate rights edit validates the new grant against the current product rules and records it in audit history. The issuance plan snapshot remains historical; it is not a live link controlling modified grants. Renewal changes license expiry only; it does not silently extend separately granted update access or change features/quotas. There is no bulk automatic reapplication of a changed plan.

Optional update rights: `null` retains the legacy unspecified behavior; `false` explicitly excludes updates; `true` grants updates until the initial plan expiry. Tokens contain `updates_allowed`/`updates_until` only when explicitly defined and `quotas` only when present. Existing features and token fields keep their meaning. Clients must implement quota checks and update entitlement checks before offering those capabilities; this server does not count application-specific usage or provide a new protected package download API. Legacy clients continue checking signature/features/binding and may ignore added claims, so they must not be relied on to enforce new quota/update restrictions. Review client upgrades before selling such plans.

## Upgrade without rewriting rights

Migration `Version20261003110323` has separately guarded columns/table/foreign key and no unsupported JSON defaults. It queues data updates through Doctrine (including in dry-run) rather than executing hidden updates. Existing license fields, activation bindings, secrets and audit history are unchanged. New nullable update/plan/quota columns impose no extra rights changes. Product allowed features are initially the union of existing license features; old installation counts are preserved even above the new-product default cap. Every existing license receives a rule snapshot using its existing features/count. The previous Contao Issue Service condition becomes a required `sla` product rule during migration. A pre-existing Contao license without `sla` remains unusable, as before; migration does not silently grant it `sla`.

Fresh products start with no features; configure their rule lists before issuing feature-bearing plans/licenses. Existing products with malformed historical feature identifiers require an explicit reviewed correction before editing their definition; migrated license snapshots are preserved. Do not reduce current rules and simultaneously edit existing license grants unless the replacement grant complies with them. Use inactive plans to retire offerings. Downgrading with issued plan/quotas/update grants is blocked; restore a reviewed backup if a rollback is essential. Run the documented complete migration chain in staging first.
