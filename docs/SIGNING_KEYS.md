# Signing-key lifecycle

`app:license:rotate` manages prepared → verification_allowed → active. Activating a replacement leaves its predecessor verification_allowed, preserving regular rotation and legacy tokens without kid. Retired and revoked keys remain in private keyring metadata and history but are excluded from verification/public-keys. Prepared keys are not trusted until explicitly published. Every mutation requires an operator identity and reason; status supplies a fingerprint that must still match when a reviewed transition executes. This is a privileged operating-system command, not a permission bypass exposed to web users. File history records operator, reason, UTC time and monotonic revision; protect and externally retain it along with audit checkpoints. Operators with full filesystem control can rewrite it.

Use prepare, status, publish with --expected, distribute trusted verification keys, then status and activate with --expected and --rollout-confirmed. Activation validates the private/public pair, publication state and explicit rollout acknowledgment. That acknowledgment is an operator check, not remote proof that every client deployed its trust configuration. Active keys cannot be retired or revoked: activate a healthy replacement first. Lifecycle changes and signing share a Symfony lock; each returned token persists its maximum expiry before being delivered. Configure a shared lock store and the same writable keyring for every instance. Independently copied writable keyrings cannot coordinate lease bounds or revocation; do not activate with that architecture. Stop/drain issuance while migrating from independent copies to shared state.

Regular retire waits until all recorded online and offline token expiries have passed. Historical keys lack complete issuance records, so they additionally require --legacy-safe-after with the last expiry verified from the operator's inventory. A fabricated cutoff is unsafe; do not estimate it from the online refresh interval. Signing a token without integer expiry marks its leases unknown. Normal retirement removes verification, including refresh of old expired tokens; customers may need a new activation. Emergency revoke ignores lease expiries and rejects that key's kid and legacy tokens immediately on this server. Already disconnected clients remain able to verify until their trusted keys are updated: server-side revocation cannot remotely invalidate offline signatures. Distribute a trusted emergency replacement/revocation update and require affected installations to reconnect.

`manifest` outputs a signed version-1 signing-key-manifest with revision, issued_at, one-hour expires_at, trusted publicKeys, active/legacy identifiers and disabled key IDs. Verify using a previously pinned trusted key, require the exact type/version, reject expired/future timestamps and revisions below the last accepted revision, then persist the revision before updating trust. Never bootstrap trust from the unsigned public-keys endpoint. Before rotation, export the published manifest while the old trusted signer is active. After compromise, signatures from the compromised key are insufficient: establish replacement trust out of band. The current real Contao validator accepts explicitly configured keys; it does not automatically process these manifests or distribute emergency revocations. Operator-managed trust updates remain required; publish/review the client revision documented in CLIENT_INTEGRATION.md.

Private old keys are retained automatically; never delete active or prepared material. After retire/revoke, completed rollback/recovery retention and verified shared backups, an operator may remove only that key's private file. Keep its public metadata/history permanently. Keep the original private.key as a deployment compatibility anchor: current deployment checks require it even when another key is active. Store private material outside public/ with directories 0700 and files 0600, retain the whole keyring and independent TOTP encryption key in controlled backups, and rotate/restage deployment archives deliberately. No automatic destructive key deletion is implemented. Lifecycle changes need no SQL migration. Existing unversioned keyrings are normalized in memory and upgraded only on a mutation or signing; old public keys and signatures are preserved.
